## 2. المسار الموصى به — أمر واحد يجهّز كل شيء

### 2.1 إنشاء مفتاح وصول مؤقت

من <https://supabase.com/dashboard/account/tokens> — يحتاج صلاحيات
(organization + project + database write). لا يُحفظ في أي ملف دائم.

### 2.2 معاينة الخطة أولًا (بلا أي اتصال بالشبكة)

```bash
npm run launch:provision -- \
  --name layla-beauty \
  --salon-name "Layla Beauty" \
  --admin-email owner@layla.om \
  --admin-name "Layla" \
  --dry-run
```

**الناتج المتوقع:** اسم المشروع، المنطقة، العدد الفعلي للـmigrations المكتشفة من
القرص (46 حاليًا)، وأول/آخر ملف. لا تُلمس الشبكة.

### 2.3 التنفيذ الفعلي

```bash
SUPABASE_ACCESS_TOKEN=sbp_xxx npm run launch:provision -- \
  --name layla-beauty \
  --salon-name "Layla Beauty" \
  --region ap-south-1 \
  --plan pro \
  --admin-email owner@layla.om \
  --admin-name "Layla"
```

> `--region ap-south-1` هي الأقرب لسلطنة عمان. `--plan pro` مُستحسن لإنتاج حقيقي:
> خطة Free تُوقف المشاريع عند الخمول، و**حماية كلمات المرور المسرّبة (HIBP) متاحة
> في Pro فقط** — وهي بند أمني مطلوب قبل عميل مدفوع.

**ما ينفّذه الأمر بالترتيب:**

| # | الخطوة | التحقق الداخلي |
|---|---|---|
| 1 | إنشاء مشروع Supabase داخل المؤسسة | كلمة مرور قاعدة بيانات قوية تُولَّد تلقائيًا |
| 2 | الانتظار حتى `ACTIVE` وسلامة REST | مهلة 10 دقائق + فحص صحة |
| 3 | استخراج المفاتيح (publishable/secret وanon/service_role) | يفصل العام عن السرّي |
| 4 | تطبيق سلسلة الـmigrations كاملة بالترتيب | اكتشاف من القرص + تسجيل كل ملف في `schema_migrations` |
| 5 | تجهيز هيكل المركز الواحد (`centers` + `center_settings`) | نفس الـUUID المعتمد |
| 6 | إنشاء مستخدم Auth الأول + العضوية + دور `ADMIN` | عبر `render-membership-bootstrap.mjs` |
| 7 | كتابة عقد البيئة | `.env` عام + `.operator.env` أسرار |

### 2.4 بوابات القبول بعد التجهيز

```bash
cp <out>/layla-beauty.env .env.local
npm run launch:preflight
```

**يجب أن يخرج `PASS`.** هذا الفحص يرفض صراحةً:
- أي بيئة غير `production`،
- أي backend غير `supabase`،
- أي مشروع Supabase عام (الديمو) كهدف إنتاجي،
- أي مفتاح سرّي في متغيّر يصل إلى المتصفح.

ثم اختبارات القبول على قاعدة البيانات:

```bash
for test_file in supabase/tests/*.sql; do
  psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 --file "$test_file"
done
```

ثم ملف اختبار واحد إضافي من السلسلة (انظر `docs/APPLY_OVERLAP_MIGRATION_DEMO_RUNBOOK.md`):

```bash
psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 \
  --file supabase/tests/20260810000003_appointment_overlap_integrity.sql
```

### 2.5 النشر على Vercel

من ملف البيئة العام، في إعدادات مشروع Vercel:

| المتغيّر | القيمة |
|---|---|
| `VITE_DATA_BACKEND` | `supabase` |
| `VITE_SUPABASE_URL` | رابط مشروع العميل |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | ✅ `sb_publishable_…` أو مفتاح anon — **وليس** `sb_secret_…` أو `service_role` |
| `VITE_CENTER_ID` | UUID مركز العميل |
| `VITE_BRANCH_MODE` | `single` |
| `VITE_ENVIRONMENT` | `production` |

⚠️ **لا تضبط `VITE_USE_DEMO_CREDENTIALS` إطلاقًا على نشر عميل.** البناء يفشل
صراحةً إذا اجتمع مع هدف صريح أو مع `production` — وهذا مقصود.

### 2.6 القبول النهائي في المتصفح (إلزامي قبل التسليم)

- [ ] الدخول بحساب المالك — والنجاح يعني أن الـbootstrap صحيح.
- [ ] Dashboard يفتح ويعرض بيانات مركز العميل (لا الديمو).
- [ ] إنشاء عميلة → تظهر بعد إعادة تحميل الصفحة.
- [ ] إنشاء موعد → تمرير الزيارة عبر المراحل حتى `READY_FOR_CHECKOUT`.
- [ ] POS: بيع خدمة، ثم منتج مخزني، ثم الدفع.
- [ ] الإيصال يطبع ويظهر باسم مركز العميل الصحيح.
- [ ] التقارير تُظهر البيع، وDashboard يتحدّث.
- [ ] مستخدم بدور `STAFF` لا يستطيع الوصول إلى `/reports` و`/settings` و`/accounting`.
- [ ] الواجهة عربية RTL على الجوال فعليًا.

## 3. المسار البديل — يدويًا من لوحة Supabase

يُستخدم فقط إذا تعذّر تشغيل المزوّد الآلي.

1. **مشروع جديد** — خطة Pro، منطقة قريبة، احفظ كلمة مرور قاعدة البيانات في مدير أسرار.
2. **تطبيق السلسلة**: نفّذ **كل** ملفات `supabase/migrations/*.sql` بترتيب اسمي
   تصاعديًّا (**46 ملفًا حاليًا**)، و**استثنِ** `20260628000002_admin_bootstrap.sql`.
   - اكتشف الملفات من المجلد وقت التنفيذ — لا تعتمد على رقم مكتوب في وثيقة.
   - لا تستخدم أي SQL من `docs/` أو `docs/archive/`؛ فهي مرجعية تاريخية فقط.
3. **إنشاء مستخدم Auth** من `Authentication → Users → Add user`، وانسخ الـUUID.
4. **تشغيل الـbootstrap**:
   ```bash
   npm run launch:membership -- \
     --user-id <UUID-من-الخطوة-3> \
     --center-id 7f0b8e2a-6d5a-4a1b-9c2d-3e4f5a6b7c8d \
     --role ADMIN \
     --name "اسم المالكة"
   ```
   الصق الناتج في SQL Editor ونفّذه مرة واحدة. السكربت يرفض نفسه إذا كان UUID
   غير حقيقي، أو إذا لم يكن مستخدم Auth موجودًا، أو إذا لم يكن المركز موجودًا.
   > إن فشل السكربت، نفّذ `ROLLBACK;` قبل إعادة المحاولة — فهو ملفوف في معاملة
   > صريحة، والفشل داخل معاملة يُبقي الجلسة في حالة إجهاض وكل جملة بعدها تفشل.
5. أكمل من الخطوة 2.4 أعلاه.

> **بديل آخر:** تعديل `v_admin_uid` داخل `20260628000002_admin_bootstrap.sql` وتنفيذه.
> الملف **يرفض** العمل إذا نُسّخ كما هو (UUID صفري) — لا يخترع مديرًا وهميًا.

| # | الإجراء | السبب |
|---|---|---|
| 1 | **إغلاق التسجيل الذاتي**: `Authentication → Providers → Email → Disable signup` | خلاف ذلك يستطيع أي شخص إنشاء حساب Auth |
